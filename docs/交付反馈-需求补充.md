# 交付反馈需求补充

## 来源

交付反馈截图，用户于需求问询阶段提供。

## 1. 汇率工资

### 反馈内容

目前有一部分客户，大约七八个人，是用外币定薪，类似公司发放的“驻外津贴”。工资可能以新币、人民币或美金计价，每个月需要根据客户认可的汇率口径，计算成当地本币，即印尼盾 IDR 后发放。

这部分与社保没有关系，属于税前工资计算标准，每个月可能因为汇率变化而发生变化。

### V1 需求含义

- 系统需要支持员工级或薪资组件级的外币计价工资。
- 系统需要按薪资月份记录客户认可的汇率。
- V1 只认客户确认汇率，不自动抓央行汇率或市场汇率。
- 汇率表按客户、薪资月份、币种维护；记录汇率、证据、确认人和确认时间。
- 系统需要把外币金额换算为 IDR 后进入税前工资/应发工资计算。
- 汇率口径、客户确认记录、原币金额、换算后 IDR 金额必须留痕。
- 外币金额换算为 IDR 后，内部计算保留高精度进入后续税/社保/实发/雇主成本计算，不在换算后立即取整。
- 导出文件需要同时展示原币金额、汇率和按取整规则得到的 IDR 展示金额。
- 外币工资默认进入 PPh21 税基。
- 外币工资默认不进入 BPJS 基数，除非客户规则明确配置。
- 汇率缺失或客户未确认时，应生成追问项/核查项，不得静默计算。

## 2. 从税后推算税前（Gross Up）

### 反馈内容

虽然当前系统还不支持，但很多客户会约定税后工资/到手工资，这会导致公司每个月计算税前预算很麻烦。

当地法律和税务允许从税后推税前。实现逻辑为：

1. 先确定到手工资。
2. 加上个人和公司各自承担的社保。
3. 倒推出总值，并计算应纳税额。
4. 将税款作为“个税补贴”项，即 Gross Up，补进计算规则里。

### V1 需求含义

- 系统需要支持 Gross Up 计算模式：以目标到手工资为输入，反推税前工资、个税补贴、社保个人/雇主承担和雇主总成本。
- Gross Up 进入 V1 P0。
- Gross Up 默认按客户级配置启用，员工级可覆盖。
- Gross Up 的税款应作为薪资组件“个税补贴 / Tax Allowance”进入计算结果。
- Gross Up 模式必须有循环校验或误差阈值，确保最终到手工资与目标到手工资一致或在允许误差内。
- Gross Up 默认成功阈值：最终到手工资与目标到手工资差异绝对值 <= IDR 1；超过 IDR 1 属于阻断项。
- Gross Up 最大迭代次数必须写入规则版本。
- Gross Up 迭代计算失败时必须阻断，不允许人工手填税前结果绕过算薪引擎。
- 如果原始 Excel 出现“税后”“到手”“Net”等字段，但客户配置或员工覆盖不是 Gross Up，系统必须阻断并要求确认计算模式。
- Gross Up 模式与三福案例不同：三福当前说明不是 Net-to-Gross 反算案例，不能用三福案例证明 Gross Up。

## 3. 算薪确认与高风险放行

### 已确认口径

- V1 不把复核设计成逐格验算。
- 普通 payroll run 由算薪人查看系统生成的算薪确认包，确认系统规则已执行、阻断项已清零、异常已解释、证据齐全、输出模板合法后锁定和导出。
- 只要命中高风险清单，必须二次确认或管理员放行后才能锁定/导出。
- 高风险放行人以算薪负责人/交付主管为主。
- 系统管理员只负责账号、角色、权限和系统配置，不参与业务 payroll 放行。
- 系统管理员默认可以查看所有客户的 payroll 明细。
- 系统管理员可以导出所有客户的 payroll 文件，但所有导出必须进入审计日志。
- 系统管理员不能绕过高风险门禁，也不能替业务 payroll run 放行。
- 客服/交付专员作为对客一线，可以导出其授权客户的 payroll 交付材料，但所有导出必须进入审计日志。
- 客服/交付专员、算薪人、算薪负责人/交付主管只能访问被授权客户的数据。

### 角色边界

- 客服/交付专员：收集客户 Excel、确认字段映射、向客户追问、回填企业微信证据、维护员工主档、导出授权客户的对客材料。
- Agent：自动解析、生成映射草稿、生成追问清单、执行预检查、解释核查结果、生成算薪确认包。
- 算薪引擎：按已发布规则版本刚性计算、执行核查阻断、校验导出模板。
- 算薪人：处理阻断项、确认普通 payroll run、锁定、导出。
- 算薪负责人/交付主管：对高风险 payroll run 做二次确认或业务放行。
- 规则管理员：发布税率、BPJS、TER、客户规则和规则版本。
- 系统管理员：管理账号、角色、权限和系统配置；默认可查看并导出所有 payroll 明细；不承担业务放行职责。

### 权限与审计补充

- 客户维度数据隔离进入 V1 P0。
- 客服/交付专员、算薪人、算薪负责人/交付主管只能查看、处理和导出其被授权客户的数据。
- 系统管理员默认可查看和导出所有客户 payroll 明细，但不能执行业务锁定、高风险放行或规则审批。
- 审计日志不可编辑、不可删除；系统管理员也不能修改或删除审计日志。
- 审计日志如需更正，只能追加更正说明，保留原始记录。

## 4. V1 默认高风险清单与阈值

### 永远高风险

- 员工主档关键字段变更：银行账号、NPWP/PTKP、BPJS、入离职、工作城市、薪资版本。
- payroll run 涉及 Gross Up。
- payroll run 涉及外币工资或员工级特殊汇率。
- 客户只给工资合计，没有项目明细。
- 字段映射低置信度，或客户确认缺证据。
- 规则版本、汇率或客户配置缺失/未发布。
- 输出人数、金额或模板结构与目标交付 Excel 不一致。
- 同一人既维护关键数据又尝试放行高风险 run。

### 环比异常阈值

- 人数与上月不一致：高风险；若新增/离职证据齐全，可由算薪人解释确认。
- 单员工实发工资环比变化超过 20% 或超过 IDR 1,000,000：高风险。
- 单员工个税环比变化超过 30%：高风险。
- 单员工 BPJS 与上月不一致：高风险，除非工资基数、参保状态或上限变化可解释。
- 客户总实发、总税、总 BPJS 任一环比变化超过 10%：高风险。

### 放行规则

- 高风险放行不是允许错算；只能允许带明确解释、证据、责任人和时间戳的特殊情况进入锁定。
- 所有高风险二次确认或放行必须进入审计日志和算薪确认包。
- 高风险阈值 V1 提供默认值，后续允许按客户配置覆盖，但客户级覆盖也必须留版本和生效月份。
- 高风险放行后，对客户交付 Excel 不显示“带风险放行”标记；内部归档的算薪确认包、审计日志和核查报告必须显示放行标记、原因、证据和责任人。

## 5. 锁定后更正规则

### 已确认口径

- payroll run 锁定后不允许原地修改。
- 锁定后发现错误，只能生成更正批次 / correction run。
- 原始 payroll run 必须保持只读，保留当时的输入文件、字段映射、规则版本、客户确认、核查报告、放行记录、导出文件和操作日志。
- correction run 必须关联原始 payroll run，并记录更正原因、更正范围、发起人、确认人、证据和时间戳。
- correction run 允许只包含受影响员工，不强制整月全量重算。
- correction run 完成后同样需要走预检查、算薪确认、高风险判断、锁定、导出和归档流程。

### V1 需求含义

- 系统需要支持 payroll run 状态机，至少包括草稿、待映射确认、待标准化确认、待客户确认、待预检查、待算薪、待算薪确认、待高风险放行、已锁定、已导出、已归档、已作废、已更正。
- 已锁定、已导出的 payroll run 只能查看、复制生成 correction run 或下载归档文件。
- 员工主档或客户配置在锁定后发生变化，不得反向影响已锁定 run，只能影响新 run 或 correction run。
- 文件、字段映射、关键算薪字段、客户规则、公共规则、汇率或客户配置变化后，系统必须按影响范围自动回退到对应阶段，不能停留在后续状态。
- 阶段回退需要记录触发原因、影响对象、触发人/系统动作、时间戳和失效的结果范围。
- 部分员工 correction run 必须在内部归档中保留原 run 全量快照、本次更正员工范围、字段差异、金额差额影响和关联证据。
- 更正批次导出的文件需要在内部归档中标记为 correction run。
- correction run 的客户交付文件名需要显示更正批次；Excel 内部结构尽量保持客户现有案例同结构，不为了标识更正而破坏交付模板。
- correction run 对客户导出时，系统应支持按交付口径选择全量重发或只导出更正员工清单。

## 6. 删除与作废规则

### 已确认口径

- 未锁定的 payroll run 可以删除。
- 已锁定或已导出的 payroll run 不能删除，只能作废并保留审计记录。
- 作废不是物理删除；系统必须保留原 run 的输入文件、字段映射、规则版本、客户确认、核查报告、放行记录、导出文件和操作日志。
- 作废操作必须记录作废原因、发起人、确认人、时间戳和关联证据。

### V1 需求含义

- 删除仅适用于草稿、预检查失败且未锁定、用户误建的 payroll run。
- 已锁定/已导出的 payroll run 进入作废状态后，不参与默认列表统计和正式交付结果，但可在归档和审计视图中查询。
- 若作废后需要重新交付，应新建 payroll run 或 correction run，不能恢复原 run 原地修改。
- 删除和作废都需要权限控制；客服可删除自己创建且未锁定的草稿 run，已锁定/已导出 run 的作废必须由算薪负责人/交付主管确认。

## 6.1 归档文件删除与替换规则

### 已确认口径

- 已关联正式 payroll run、已锁定 run、已导出 run、发薪记录、申报证据或客户确认的归档文件，不允许物理删除。
- 归档文件发现错误时，只能作废或上传替换版本，并保留版本和审计记录。
- 误上传且尚未关联任何正式对象的草稿附件，可以删除。

### V1 需求含义

- 归档文件至少包括：原始输入 Excel、字段映射版本文件、标准化数据快照、算薪确认包、核查报告、导出 Excel、发薪付款证据、KS/TK 申报凭证、PPh21 申报证据、客户确认截图/文本。
- 作废归档文件必须记录作废原因、发起人、确认人、时间戳和替代文件。
- 替换归档文件必须保留原文件版本、替换后文件版本、替换原因、操作人、确认人和时间戳。
- 被作废的归档文件不参与默认交付结果展示，但必须能在审计和归档视图中查询。
- 删除草稿附件需要权限控制和操作日志。

## 6.2 客户停用与归档

### 已确认口径

- V1 客户管理需要支持客户停用/归档。
- 已存在 payroll 历史、归档文件、发薪记录、申报证据或客户确认记录的客户，不允许物理删除。
- 客户停用后不能新建 payroll run，但历史归档仍可查询。

### V1 需求含义

- 客户状态至少包括：启用、停用。
- 停用客户必须记录停用原因、操作人、确认人和时间戳。
- 停用客户不出现在默认新建 payroll run 的客户选择列表中。
- 停用客户的历史 payroll run、归档文件、发薪记录、申报证据、员工主档版本和客户配置版本必须保留可查。
- 如果停用客户需要重新服务，应由有权限用户重新启用，并记录原因和审计日志。
- 从未产生正式业务数据的误建客户，可以按草稿数据删除规则处理，但必须保留操作日志。

## 6.3 员工主档停用与删除

### 已确认口径

- 已存在 payroll 历史、发薪记录、申报证据、员工主档版本或客户确认记录的员工，不允许物理删除。
- 员工离职或不再服务时，应通过离职/停用状态处理。
- 误建且未关联任何 payroll run 或正式业务数据的员工，可以删除。

### V1 需求含义

- 员工状态至少包括：在职、离职、停用。
- 离职员工必须记录离职日期、离职原因、来源证据、操作人、确认人和时间戳。
- 停用员工不出现在默认新建 payroll run 的候选员工列表中，但历史 payroll、发薪记录、申报证据和主档版本必须可查。
- 有历史 payroll 的员工不得物理删除；如需排除后续算薪，应维护离职或停用状态。
- 误建员工删除需要权限控制和操作日志。
- 员工重新启用或离职后返聘，需要生成新的员工主档版本，并记录原因和证据。

## 7. 基础数据版本与快照

### 已确认口径

- 客户级配置、员工主档、算薪规则版本等基础数据，V1 必须做版本化。
- 每次 payroll run 必须绑定当时生效的数据快照，不能引用会被后续修改污染的“当前值”。
- 已锁定 payroll run 绑定的快照永久只读；后续修改客户配置、员工主档或规则版本，不得反向影响已锁定 run。

### V1 需求含义

- payroll run 至少需要绑定以下快照：客户配置版本、员工主档版本、薪资组件/固定薪资版本、字段映射版本、汇率表版本、规则参数版本、原始输入文件版本。
- 基础数据每次变更都生成新版本，记录变更字段、变更前后值、发起人、确认人、来源证据、原因和时间戳。
- 员工主档、客户配置或汇率在未锁定 run 期间发生变更时，相关 run 必须自动变为“需重新预检查/需重算”。
- 基础数据版本需要支持按生效日期或薪资月份生效，避免本月维护下月数据时影响当前 payroll run。
- 规则版本由规则管理员发布；Agent 可以提示规则缺失、冲突或疑似过期，但不能自行修改或发布规则版本。
- 系统应提供版本差异查看，用于算薪确认、高风险放行、correction run 和历史追溯。

## 8. 员工主档变更证据要求

### 已确认口径

- 客服/交付专员可以修改员工主档。
- 员工主档关键字段变更必须绑定证据。
- 员工主档非关键字段可以无证据修改，但必须保留操作日志和版本差异。

### 关键字段范围

- 银行账号。
- NPWP/PTKP。
- BPJS。
- 入职、离职。
- 工作城市。
- 薪资版本。
- Gross Up 员工级覆盖。
- 员工级特殊汇率。

### V1 需求含义

- 修改关键字段时，系统必须要求选择或上传证据；没有证据不得保存为生效版本。
- 关键字段变更必须进入算薪确认包和高风险清单。
- 如果关键字段变更影响未锁定 payroll run，相关 run 必须自动变为“需重新预检查/需重算”。
- 如果关键字段变更发生在 payroll run 锁定后，不得反向影响已锁定 run，只能影响新 run 或 correction run。
- 系统必须记录变更字段、变更前后值、变更人、确认人、证据、原因、时间戳和生效月份。

### 有效证据类型

- 客户原始 Excel。
- 企业微信客户回复截图或文本。
- 客户补充文件。
- 官方 BPJS、税务、银行文件。
- 客服手写备注只能作为说明，不能单独作为关键字段生效证据。

## 9. Agent 字段映射置信度

### 已确认口径

- Agent 可以生成字段映射草稿，但不能让映射自动生效。
- 映射生效必须由人工确认。
- V1 不依赖单一自动分数直接决定生效，只分高置信、中置信、低置信/冲突三档处理。

### 三档处理

- 高置信：可进入待人工确认，显示源字段、目标字段、样例值和判断依据。
- 中置信：必须展示判断原因和候选字段，由客服/交付专员人工确认。
- 低置信/冲突：不得进入映射确认，必须生成追问项或要求人工选择。

### V1 需求含义

- 字段映射确认前，系统必须展示源 sheet、源列名、样例值、目标标准字段、置信档位和 Agent 判断依据。
- 低置信/冲突映射属于高风险，不得静默进入算薪。
- 映射确认后生成字段映射版本，并绑定到 payroll run。
- 已确认映射可沉淀为客户字段映射模板，但后续复用时仍需展示差异并由人工确认。
- 客户字段映射模板允许用于预填映射；不允许自动生效。
- 同客户、同模板结构、同 sheet/列名/样例稳定时，系统可预填映射，但仍必须由客服/交付专员点击确认后才能进入标准化数据预览。

## 10. 标准化数据预览与修改

### 已确认口径

- 字段映射确认后，系统进入标准化数据预览确认。
- 客服/交付专员可以在标准化数据预览中修改数据。
- 非关键字段可直接修改，但必须留操作日志。
- 关键算薪字段修改必须绑定证据，保存后触发重新预检查，并进入高风险清单。
- 标准化数据预览支持批量确认无异常员工；异常员工必须逐项处理。
- 同一 payroll run 同一对象被多人同时编辑时，V1 使用乐观锁处理并发编辑。

### 关键算薪字段范围

- 员工身份匹配字段。
- 入职、离职。
- 工作城市。
- 薪资组件和金额。
- 币种、汇率、原币金额。
- Gross Up 目标金额或员工级 Gross Up 覆盖。
- PTKP、NPWP。
- BPJS 参保状态、基数、编号。
- 银行账号。
- 考勤、请假、加班、调薪、THR、离职补偿等会影响算薪结果的输入。

### V1 需求含义

- 标准化数据预览必须展示源文件来源、源 sheet、源行列、标准字段、标准化后值、修改状态和证据状态。
- 标准化数据修改后必须生成数据版本，并绑定到 payroll run。
- 关键算薪字段缺证据时不得保存为生效版本。
- 修改关键算薪字段后，已完成的预检查、算薪结果和核查结果必须失效，相关 run 自动回到“需重新预检查/需重算”。
- 修改关键算薪字段后，已基于旧版本结果取得的客户确认必须失效。
- 保存时如果系统发现对象版本已被他人修改，必须提示刷新/合并，不得覆盖他人修改。
- 批量确认只适用于无阻断、无高风险、无低置信映射、无关键字段缺证据的员工记录。
- 系统需要保留修改前后差异，供算薪确认、高风险放行和 correction run 使用。

## 11. 客户确认与证据关联

### 已确认口径

- 客户回复证据不能只挂在追问问题上，也要能挂到具体字段、员工、payroll run 和客户口径。
- 一个证据可以同时关联多个对象。
- 一个对象也可以关联多条证据。
- 客户确认可以覆盖全 payroll run、部分员工、部分字段或某个客户口径；系统必须记录确认覆盖范围。
- 证据默认只对关联薪资月份/payroll run 生效。
- 客户长期口径需要升级为客户规则或客户配置版本。
- 手工备注可以解释操作原因，但不能单独解除阻断项或高风险项。

### 证据可关联对象

- 客户。
- 薪资月份。
- payroll run。
- 原始输入文件。
- sheet、行、列、单元格。
- 字段映射。
- 标准化字段。
- 员工。
- 员工主档版本。
- 薪资组件。
- 规则/客户口径。
- 追问问题。
- 高风险项。
- correction run。

### V1 需求含义

- 证据记录必须包含证据类型、来源、内容/附件、上传人、确认人、时间戳、关联对象、适用月份和备注。
- 客户确认证据必须记录覆盖范围：全 run、员工范围、字段范围、客户口径范围或文件范围。
- 企业微信客户回复截图/文本需要作为证据记录进入系统，而不是只停留在服务群。
- 客户基于草稿/预览材料给出的核对反馈，需要作为证据或追问回复进入系统。
- 客户核对反馈如果是“确认无误”，也必须回填为客户确认证据。
- 客户确认只对对应的数据版本、算薪结果版本和导出预览版本有效；关键算薪字段变化后，原客户确认不得继续覆盖新结果。
- 客户确认失效后，系统必须要求重新预检查，并根据影响范围要求重新客户确认或内部确认。
- 影响对客结果的金额、员工范围、银行、税/社保、输出模板字段变化，必须重新客户确认。
- 只影响内部解释、备注、审计分类的变化，可以只做内部确认。
- Agent 可以建议“需要客户确认”或“只需内部确认”的分类和理由，但最终由客服/算薪人确认。
- 明确规则命中的客户确认缺失、确认失效或关键字段变更，系统必须自动阻断。
- Agent 生成追问清单时，需要把每个问题预关联到字段、员工、sheet 或客户口径。
- 客服回填证据后，系统应提示该证据可解决哪些追问项或阻断项，但最终关联生效需要人工确认。
- 手工备注可作为证据的补充说明，但不能单独作为有效证据解除阻断或高风险。
- 算薪确认包、核查报告、审计日志和归档视图必须能从结果反查到证据。
- V1 只支持企业微信证据人工上传/粘贴，不接企业微信接口自动同步。
- 企业微信接口自动同步列为 P1，不影响 V1 验收。

## 12. Agent 追问清单状态规则

### 已确认口径

- Agent 生成的追问问题，客服/交付专员可以关闭，但不能物理删除。
- 关闭追问问题必须选择原因，并保留审计记录。
- Agent 不确定时必须生成追问、低置信提示或阻断项。
- Agent 不得编造字段映射、客户口径或规则解释。

### 关闭原因

- 已由其他证据解决。
- 客户确认无需提供。
- 系统判断误报。
- 转规则配置处理。

### V1 需求含义

- 追问问题至少包含状态：待处理、已发送客户、待客户回复、已回填证据、已解决、已关闭。
- 关闭记录必须包含关闭原因、关闭人、时间戳、关联证据或说明。
- 如果追问问题关联阻断项，关闭前必须确认阻断项是否已解决；未解决不得进入正式算薪。
- 关闭追问问题不能删除历史，算薪确认包和审计日志仍需可追溯。

## 12.1 Agent 会话上下文与 Trace

### 已确认口径

- 同一个 payroll run 内，Agent 必须持续带着客户、薪资月份、文件、字段映射、追问、证据、核查结果上下文。
- Agent 的关键建议、映射依据、追问生成依据、核查解释都要留 trace，并归档到 payroll run。

### V1 需求含义

- Agent 上下文至少包含：客户、薪资月份、payroll run 状态、上传文件、字段映射版本、标准化数据版本、追问清单、证据、阻断项、高风险项、算薪结果、核查报告、导出预览。
- Agent 在算薪、复核、导出阶段需要接续同一 payroll run 上下文，不能把每一步当成孤立对话。
- Agent trace 至少记录：触发人、触发时间、输入上下文、建议内容、判断依据、关联字段/员工/文件、置信档位、人工确认结果。
- Agent trace 只能作为解释和追溯材料，不得替代确定性算薪引擎、规则版本或人工确认。
- payroll run 锁定后，对应 Agent trace 随归档包一起归档。

## 12.2 Agent 资料库、降级与成本控制

### 已确认口径

- 法规、内部 SOP、客户规则说明可以作为 Agent 查询资料库/RAG。
- 资料库回答不能替代已发布规则版本。
- Agent 服务不可用时，系统仍允许人工导入、映射、预检查、算薪和导出；只是没有 AI 建议。
- V1 需要记录每次 Agent 调用的模型、token/成本、耗时和状态。
- 超预算时停止 Agent 建议，不影响确定性流程。

### V1 需求含义

- Agent 查询资料库时，回答必须引用资料来源或关联资料条目。
- Agent 基于资料库给出的法规、SOP、客户口径解释，只能作为提示、追问建议或核查解释，不得直接改写规则版本。
- 税率、BPJS 上限、TER 表、PTKP、THR、加班、客户算薪规则等正式计算参数，只能来自已发布规则版本。
- Agent 服务不可用、超时、报错或超预算时，系统需要提示“AI 建议不可用”，但不阻断确定性工作流。
- 人工流程至少包括：上传文件、人工映射、标准化确认、预检查、算薪、核查、确认锁定、导出。
- Agent 调用记录至少包含：payroll run、触发人、功能类型、模型、token 用量、估算成本、耗时、状态、错误信息和输出摘要。
- 成本超预算后，系统停止继续生成 Agent 建议，并允许用户继续完成非 AI 流程。

## 12.3 记忆机制

### 已确认口径

- V1 需要显式区分客户级记忆、全局级记忆和 Run 上下文记忆。
- 记忆不是聊天缓存，必须落到可版本化、可审计、可引用的数据对象。
- Agent 可以读取记忆、引用记忆、建议复用记忆，但不能自动让记忆生效。
- 记忆生效必须通过人工确认、客户配置版本、客户规则版本、字段映射版本或已发布公共规则版本。
- 记忆失效必须能被系统识别，并触发追问、预检查、重算、客户确认失效或高风险/阻断项。

### 客户级记忆

客户级记忆用于同一客户后续薪资月份复用，至少包括：

- 客户主档与合作配置。
- 客户字段映射模板。
- 客户薪资组件别名映射。
- 客户长期口径。
- 客户规则版本。
- 客户汇率确认历史。
- 客户历史 payroll run。
- 客户历史阻断项、高风险项和处理方式。
- 客户历史确认记录和证据。
- 客户输出模板配置和文件命名规则。

客户级记忆只能在同一客户范围内复用；跨客户复用必须先升级为全局规则、全局字典或人工确认的新客户配置。

### 全局级记忆

全局级记忆用于所有客户，至少包括：

- 公共法规规则版本。
- TER、PTKP、Pasal 17、BPJS、UMP/UMK、THR、加班、假期等规则参数。
- 系统级薪资组件字典。
- 字段字典及中文、英文、印尼语别名。
- 内部 SOP。
- 法规/规则资料库。
- 蓝色光标和三福回归样例。
- 通用核查规则和默认高风险阈值。
- 通用输出模板结构能力。

全局级记忆用于确定性计算时，必须来自已发布规则版本或系统级字典版本；RAG 资料库只能辅助 Agent 解释、追问和核查，不得替代已发布规则。

### Run 上下文记忆

Run 上下文记忆只服务当前 payroll run，至少包括：

- 当前客户、薪资月份、负责人、状态机阶段。
- 上传文件和文件版本。
- 字段映射草稿、确认版本和置信信息。
- 标准化数据版本。
- 追问清单和客户回复。
- 证据和证据关联对象。
- 阻断项和高风险项。
- 预检查结果、算薪结果、核查报告。
- 算薪确认包、导出预览、导出文件。
- Agent trace 和人工确认记录。

Run 上下文记忆随 payroll run 锁定和归档形成只读快照；后续不得被新配置、新规则或新主档反向污染。

### 记忆生效规则

- 客户级记忆被复用时，系统必须展示来源、版本、适用范围和差异。
- 字段映射模板、客户组件别名、客户长期口径可预填，但不得自动生效。
- 客户长期口径要长期生效，必须升级为客户配置版本或客户规则版本。
- 全局规则要参与正式计算，必须是已发布规则版本。
- Agent 从记忆中提出建议时，必须给出引用来源和适用理由。
- 人工确认后，记忆复用结果需要绑定到 payroll run 快照。

### 记忆失效规则

- 客户配置、客户规则、字段映射模板、薪资组件字典、汇率表、员工主档或公共规则版本变化时，相关记忆可能失效。
- 原始文件结构、sheet、表头、样例值与历史模板不一致时，历史字段映射记忆不得自动生效。
- 客户确认只对对应数据版本、算薪结果版本和导出预览版本有效；关键算薪字段变化后，相关客户确认记忆失效。
- 临时客户口径默认只对当期 payroll run 有效，到期不得自动复用。
- 记忆失效后，系统必须按影响范围触发追问、重新映射、重新预检查、重算、重新客户确认、高风险项或阻断项。

## 13. 阻断项与高风险项

### 已确认口径

- 阻断项和高风险项必须分开。
- 阻断项不解决，就不能进入对应阶段。
- 高风险项可以完成计算，但锁定/导出前必须二次确认或业务放行。

### 阻断项

阻断项是不解决就不能算薪、锁定或导出的硬错误，例如：

- 缺少必填输入字段。
- 缺少客户确认且该确认影响算薪规则。
- 关键字段无有效证据。
- 汇率缺失或未确认。
- 规则版本缺失、未发布或与薪资月份不匹配。
- 客户配置缺失。
- 客户规则缺失且影响金额、税、社保、Gross Up、THR 或离职清税。
- 字段映射未确认。
- 标准化数据未确认。
- 算薪引擎计算失败。
- 算薪引擎计算 trace 不完整。
- 输出模板结构不合法。
- 输出人数或必要金额校验不通过。

### 高风险项

高风险项是允许完成计算，但锁定/导出前必须二次确认或业务放行的风险信号，例如：

- 员工主档关键字段变更。
- Gross Up。
- 外币工资或员工级特殊汇率。
- 客户只给工资合计，没有项目明细。
- 社保账单不完整或与系统计算差异超过阈值。
- 环比异常波动超过默认或客户级阈值。
- 字段映射中置信或历史模板差异较大。
- 同一人既维护关键数据又尝试放行高风险 run。

### V1 需求含义

- 系统需要分别展示阻断项数量和高风险项数量。
- 阻断项必须清零后才能正式算薪、锁定或导出。
- 高风险项必须完成二次确认或业务放行后才能锁定/导出。
- 算薪确认包必须分开展示阻断项处理结果和高风险项放行记录。
- 客户规则缺失但不影响计算结果的，可生成提示项，不阻断算薪。
- 算薪引擎报错或计算 trace 不完整时，payroll run 必须阻断；不得只给“计算失败”后让人工手工补结果。

## 14. 算薪确认包展示方式

### 已确认口径

- 算薪人确认 payroll run 时，不默认逐格查看全量明细。
- 算薪确认包主界面先展示摘要和异常，再按需下钻。
- 全量明细需要支持查询和下载，但不作为主确认界面的默认阅读方式。

### 主界面内容

- 本期总览：客户、薪资月份、人数、应发合计、实发合计、PPh21、BPJS KS/TK、雇主成本、离职人数、Gross Up 人数、外币工资人数。
- 阻断项处理结果：阻断项数量、状态、处理人、处理时间、关联证据。
- 高风险项清单：风险类型、影响员工/金额、解释、放行状态、二次确认人。
- 环比差异摘要：本月 vs 上月人数、应发、实发、个税、BPJS、员工级变化。
- 客户确认摘要：关键客户口径、追问问题、证据状态。
- 输出校验摘要：目标模板、sheet、人数、金额、结构校验结果。

### 下钻内容

- 员工级算薪明细。
- 字段映射证据。
- 标准化数据修改记录。
- 员工主档版本差异。
- 算薪规则版本和参数快照。
- 原始文件定位。
- 高风险放行记录。
- correction run 差额影响。

### V1 需求含义

- 算薪确认包需要支持从摘要跳转到员工、字段、证据、规则版本和原始文件。
- 全量明细可导出或在明细页查询，但不能替代异常驱动确认流程。
- 算薪人点击确认锁定前，系统必须再次校验阻断项清零、高风险项已放行、输出模板合法。

## 15. 导出预览与模板校验

### 已确认口径

- 算薪人确认锁定前，必须看到导出 Excel 预览。
- V1 不要求在线打开完整 Excel，但必须展示目标 workbook、sheet 列表、行数、关键汇总金额和模板结构校验结果。

### 预览内容

- 导出文件类型和文件名。
- 目标交付模板版本。
- workbook 数量。
- 每个 workbook 的 sheet 列表。
- 每个 sheet 的行数、列数和关键字段。
- 关键汇总金额：应发、实发、PPh21、BPJS KS/TK、雇主成本。
- 人数校验：标准化数据人数、算薪结果人数、导出人数。
- 模板结构校验：sheet 名称、表头、必要列、公式列、格式要求。

### V1 需求含义

- 输出模板结构不合法属于阻断项。
- 导出预览需要绑定到算薪确认包，锁定后随 payroll run 一起归档。
- 导出文件必须与现有真实案例同结构；如果无法匹配目标模板，系统不得正式导出。
- correction run 的导出预览也必须显示更正批次文件名、导出范围和差额影响。
- 点击正式导出时，系统必须重新校验：payroll run 已锁定、阻断项已清零、高风险项已放行、输出模板合法、客户确认未失效。
- 正式导出成功后，系统必须自动生成归档包。
- 归档包至少包含：导出文件、算薪确认包、核查报告、规则快照、输入文件、证据索引、审计日志索引。
- V1 需要按客户模板配置维护文件命名规则。
- 正式、草稿、预览、correction run 文件名必须可区分。

## 15.1 导出权限与审计

### 已确认口径

- 系统管理员可以导出所有客户的 payroll 文件。
- 客服/交付专员可以导出其授权客户的 payroll 交付材料。
- 所有导出操作必须进入审计日志。
- 未锁定 payroll run 不能导出正式交付 Excel。
- 未锁定 payroll run 只能导出带“草稿/预览”标识的内部核对材料。
- 草稿/预览材料可以发给客户核对，但必须明显标识“非正式结果/仅供核对”。
- 正式对客 Excel 只能在 payroll run 锁定后导出。

### V1 需求含义

- 导出审计日志至少记录：导出人、角色、时间、客户、薪资月份、payroll run、文件类型、文件名、导出范围、导出目的和来源 IP/设备信息。
- 客服/交付专员、算薪人、算薪负责人/交付主管、系统管理员的导出行为都必须记录。
- 客服/交付专员只能导出其被授权客户的材料。
- 未锁定 run 的导出文件必须在文件名和文件内容中明确标识“草稿/预览”或“非正式结果/仅供核对”，不得使用正式交付文件名。
- correction run 文件名必须显示更正批次。
- 如果草稿/预览材料用于客户核对，导出目的必须记录为“客户核对”。
- 客户基于草稿/预览材料反馈的修改，必须回填系统形成证据、追问或标准化数据修改记录。
- 客户基于草稿/预览材料回复“确认无误”时，也必须回填系统形成客户确认证据。
- 不得直接在系统外修改 Excel 后作为正式结果上传。
- 已锁定/已导出 payroll run 的文件下载也属于导出行为，必须记录审计。
- 系统管理员可导出不等于可放行；高风险放行仍只能由算薪负责人/交付主管执行。
- 客服/交付专员可导出不等于可锁定或放行；锁定仍由算薪人执行，高风险放行仍由算薪负责人/交付主管执行。
- 审计日志不得被任何用户修改或删除；如需更正，只能追加更正说明。

## 15.2 任务提醒与统一操作入口

### 已确认口径

- V1 只做系统内任务提醒和状态，不接邮件或企业微信自动通知。
- 所有导入、映射、追问、预检查、算薪、确认、导出，都从 payroll run 任务详情页进入。
- V1 不做散落入口。

### V1 需求含义

- payroll run 任务详情页是 V1 主操作入口。
- 任务详情页需要展示当前阶段、待处理动作、阻断项、高风险项、追问项、客户确认状态、导出状态和归档状态。
- 系统内任务提醒至少覆盖：待上传文件、待确认映射、待确认标准化数据、待客户回复、待预检查、待算薪、待处理阻断、待高风险放行、待锁定、待导出、待归档。
- 用户从提醒进入时，必须落到对应 payroll run 任务详情页和具体待处理区域。
- 邮件通知、企业微信自动通知、企业微信群消息自动发送列为 P1 或后续范围，不影响 V1 验收。

## 15.3 任务台、查询与基础非功能

### 已确认口径

- V1 任务台只显示交付运营指标，不做经营分析大屏。
- V1 P0 支持按客户、月份、状态、负责人、阻断/高风险、员工姓名/ID 搜索 payroll run 和员工记录。
- 银行账号、证件号、NPWP 默认脱敏展示；有权限用户可点击查看明文，查看明文必须进入审计。
- V1 支持 Excel 解析后的表格预览和截图/图片证据预览；不要求在线编辑 Excel。
- V1 先按单个 payroll run 1,000 名员工、20 个 Excel、单文件 50MB 以内设计。
- 超过文件大小、员工数或文件数限制时，系统阻断上传或进入导入失败，并给出处理建议。
- V1 界面中文为主；字段字典支持中文、英文、印尼语别名。
- 所有审计、确认、导出、锁定时间用系统统一时区记录；界面显示本地时间。

### V1 需求含义

- 任务台指标至少包括：待处理 run、阻断项数量、高风险项数量、待客户确认数量、逾期任务数量。
- 任务台不展示收入、利润、客户经营分析、人员成本趋势等经营分析指标。
- payroll run 列表需要支持按客户、薪资月份、状态、负责人、阻断状态、高风险状态筛选。
- 员工记录需要支持按员工姓名、员工唯一 ID、NIK/护照、NPWP 搜索；敏感字段搜索结果默认脱敏展示。
- 敏感字段查看明文需要权限控制，并记录查看人、角色、时间、客户、员工、字段类型和原因。
- Excel 表格预览用于核对解析结果、sheet、表头、样例值和原始单元格位置；不得在预览中直接编辑原始 Excel。
- 截图/图片证据预览用于核对客户回复、付款凭证、申报凭证等证据材料。
- 导入超过限制时，系统需要说明超限项、当前值、限制值和建议处理方式，例如拆分文件、分批上传或联系管理员。
- 字段字典别名需要支持中文、英文、印尼语，用于 Agent 字段识别、人工映射确认和客户模板配置。
- 时间戳存储需要统一时区和格式；界面可以按用户本地时间显示，但审计详情必须能看到系统记录时间。

## 15.4 责任人、逾期与内部协作

### 已确认口径

- V1 逾期只按 payroll run 的目标完成日期/发薪日倒推，不做复杂 SLA 配置。
- payroll run 需要有客服负责人、算薪负责人、业务放行人三个责任字段。
- 负责人变更必须留审计；未完成任务随负责人转移。
- V1 支持 payroll run 内部评论，用于交接和解释。
- 内部评论不能替代证据。
- 客户长期口径沉淀到客户配置/客户规则；临时口径只挂当期 payroll run。

### V1 需求含义

- payroll run 至少记录：客服负责人、算薪负责人、业务放行人、目标完成日期、发薪日。
- 逾期判断基于目标完成日期；如果没有目标完成日期，则基于发薪日倒推规则生成提醒。
- V1 不提供复杂 SLA 规则配置，例如按客户等级、阶段、任务类型配置不同 SLA。
- 负责人变更需要记录原负责人、新负责人、变更人、变更原因、时间戳和未完成任务转移范围。
- 未完成任务包括：待上传文件、待映射确认、待标准化确认、待客户确认、待预检查、待算薪、待高风险放行、待锁定、待导出、待归档。
- 内部评论需要关联 payroll run、员工、字段、阻断项、高风险项或文件。
- 内部评论可以解释交接背景、处理原因和注意事项，但不能单独解除阻断项、高风险项或客户确认要求。
- 临时客户口径仅对当期 payroll run 生效；如需长期复用，必须升级为客户配置版本或客户规则版本，并按规则发布/确认流程处理。

## 16. V1 输出模板范围

### 已确认口径

- V1 先内置蓝色光标和三福两个真实案例模板。
- V1 不做通用模板编辑器。
- 系统需要抽象“客户模板配置”数据结构，为后续新增客户模板预留扩展口。

### V1 需求含义

- 蓝色光标模板必须支持导出现有案例同结构的对客薪酬明细、BPMP 在职个税报盘、BPA1 离职个税报盘等文件。
- 三福模板必须支持导出现有案例同结构的 SUM 底表/对客交付文件，具体以 docs 里的三福真实案例输出为准。
- 每个客户模板配置至少包含 workbook、sheet、表头、字段来源、公式列、汇总校验、格式要求和文件命名规则。
- 模板结构校验失败属于阻断项。
- 新增客户模板能力列为后续扩展，不作为 V1 必须交互功能；但底层数据模型不能写死到只能支持两个客户。

## 17. V1 原始输入导入验收

### 已确认口径

- 蓝色光标和三福都必须支持从 docs 里的原始客户 Excel 重新导入并复算。
- V1 验收不能只导入人工整理后的中间表。
- 人工整理后的中间表可以作为对照样本、回归测试样本或导出目标参考，但不能作为唯一输入路径。

### V1 需求含义

- 蓝色光标必须从员工档案、入离转调、请假、加班、调薪等原始输入 Excel 开始导入，完成字段映射、标准化、预检查、算薪、核查、确认锁定和导出。
- 三福必须从多门店、多 sheet 的原始工资/考勤 Excel 开始导入，完成门店/sheet 识别、字段映射、标准化、预检查、算薪、核查、确认锁定和导出。
- 系统必须保留原始输入文件版本，并把标准化数据、字段映射和算薪结果反向关联到原始 sheet、行、列或单元格。
- 如果系统只能导入清洗后的中间表，不能算作 V1 跑通真实案例。
- V1 回归验收需要覆盖蓝色光标和三福两条端到端路径：原始 Excel 导入 -> 字段映射 -> 标准化数据确认 -> 预检查 -> 算薪 -> 核查 -> 算薪确认/高风险放行 -> 锁定 -> 导出同结构 Excel -> 归档。

## 17.1 原始文件上传与版本

### 已确认口径

- V1 P0 支持 `.xlsx` 和 `.xls` 原始 Excel 文件。
- CSV 暂不作为 V1 必须路径，除非真实案例后续明确需要。
- 一个 payroll run 必须支持上传多个原始 Excel。
- 客户补新文件或重传文件时，不覆盖旧文件；必须生成新文件版本，并标记替代关系。
- 加密、损坏、无法解析、缺 sheet、缺表头的 Excel，进入阻断项，Agent 生成追问或处理建议。

### V1 需求含义

- 每个上传文件至少记录：文件名、文件类型、文件版本、文件用途、来源、上传人、上传时间、关联客户、薪资月份、payroll run。
- 文件用途至少支持：员工档案、入离转调、请假、加班、调薪、THR、门店工资/考勤、社保账单、客户确认、对照样本、其他。
- 多文件导入时，系统需要展示每个文件的解析状态、识别 sheet、字段映射状态和阻断项。
- 文件重传需要记录被替代文件、替代原因、上传人、时间戳和影响范围。
- 文件重传后，相关字段映射、标准化数据、预检查、算薪结果和核查结果必须根据影响范围失效，并提示重新处理。
- 异常 Excel 不得静默跳过；必须在 payroll run 任务详情中展示阻断原因和下一步建议。

## 18. 原始 Excel 追溯信息

### 已确认口径

- 原始 Excel 导入后，系统需要保留原始公式和合并单元格信息。
- V1 至少保留原始 workbook、sheet、单元格地址、原始值、显示值、公式文本和合并单元格范围。
- V1 不执行或重算原始 Excel 公式；只读取公式文本和当前显示值。
- 正式算薪必须走系统算薪引擎，Excel 公式只能作为输入证据、线索或对照。

### V1 需求含义

- 导入解析结果必须能追溯到原始文件版本、sheet 名称、行号、列号和单元格地址。
- 如果单元格包含公式，系统必须保存公式文本和计算后的显示值。
- 如果单元格属于合并单元格，系统必须保存合并范围，并在字段识别、表头识别和数据抽取时正确处理。
- Agent 生成字段映射草稿时，需要能引用原始 sheet、列、样例值、公式或合并单元格信息作为判断依据。
- 算薪确认包、核查报告和归档视图需要支持从标准化字段反查到原始 Excel 位置。
- 系统不得把客户 Excel 公式结果直接视为正式算薪结果；如果 Excel 显示值与系统算薪引擎结果不一致，应生成核查项或对照差异。

## 19. 客户计算值与系统计算值

### 已确认口径

- 客户 Excel 里已经算好的税后工资、税、社保等结果可以导入。
- 这些值只能作为“客户计算值/对照值”，不参与系统正式算薪。
- 正式工资、税、社保、雇主成本等结果必须来自系统算薪引擎。

### V1 需求含义

- 字段映射时，需要区分“输入字段”和“客户计算值/对照字段”。
- 客户计算值应保留原始来源、字段名、sheet、行列、显示值和公式文本。
- 系统计算完成后，应支持把系统计算值与客户计算值做差异核查。
- 差异超过阈值时生成核查项或追问项。
- 客户计算值不得覆盖系统计算值；如需采用客户特殊口径，必须先维护为客户规则或客户配置版本，再由算薪引擎重新计算。

### V1 默认差异阈值

- 金额类差异绝对值超过 IDR 1,000：生成提示/核查项。
- 金额类差异绝对值超过 IDR 10,000：进入高风险清单。
- 人数、员工匹配、模板结构必须完全一致；不一致属于阻断项。

## 20. 员工匹配规则

### 已确认口径

- 原始 Excel 员工必须匹配到员工主档后，才能进入正式算薪。
- 姓名单独匹配只能作为低置信结果，必须人工确认。

### 匹配优先级

1. 员工唯一 ID。
2. NIK / 护照。
3. NPWP。
4. 姓名 + 入职日期 / 门店 / 职位组合。
5. 姓名单独匹配。

### V1 需求含义

- 高优先级唯一字段完全匹配时，可进入待人工确认。
- 多个员工命中同一匹配条件时，属于冲突匹配，不得自动确认。
- 姓名单独匹配必须标记为低置信，生成待人工确认项。
- 未匹配员工属于阻断项；不得进入正式算薪。
- 导入发现员工主档不存在时，客服/交付专员可以在流程中直接新建员工。
- 新员工需要创建员工主档版本，并绑定原始 Excel 或客户确认作为证据。
- 新员工必须进入高风险清单。
- 离职员工、重名员工、证件号缺失员工必须进入高风险或阻断清单，按证据和匹配结果处理。

## 21. 同员工多行处理

### 已确认口径

- 同一客户、同一薪资月份中，同一个员工出现在多行时，系统不能默认报错，也不能静默合并。
- 系统需要先识别多行出现的原因，再决定合并、核查或阻断。

### V1 处理规则

- 多个薪资组件行：合并到同一员工的不同薪资组件。
- 多门店或多 sheet 重复出现：生成重复核查项，要求确认是否重复发薪、跨门店分摊或数据重复。
- 同一标准字段出现多值冲突：阻断，必须人工确认或补充客户证据。
- 同一员工多行合并后，必须保留每一行的原始 Excel 来源和合并规则。

### V1 需求含义

- 标准化数据预览需要展示同员工多行合并结果和来源明细。
- Agent 可以建议多行归因，但不能自动让冲突字段生效。
- 多行处理结果需要进入算薪确认包；命中重复或冲突时进入高风险或阻断清单。

## 22. 门店维度

### 已确认口径

- 三福等多门店场景中，门店维度 V1 先作为组织、追溯和核查维度。
- 门店维度默认不直接影响算薪规则。
- 如果客户存在门店级算薪口径，必须维护为客户规则版本，不能作为隐形特殊逻辑处理。

### V1 需求含义

- 原始 Excel 的门店、sheet、部门、组织信息需要进入标准化数据。
- 算薪确认包和核查报告应支持按门店筛选、汇总和查看异常。
- 多门店员工重复、跨门店分摊、门店缺失等情况需要生成核查项。
- 门店级规则必须有客户确认或规则配置版本；没有明确规则时，门店不得改变税、社保或工资计算结果。

## 23. 薪资组件字典与客户别名

### 已确认口径

- V1 需要系统级薪资组件字典。
- V1 需要客户级薪资组件别名映射。
- Agent 可以建议客户字段映射到哪个标准薪资组件，但不能自动新增标准组件，也不能自动决定入税、入社保或是否发放。
- 新增标准薪资组件、决定入税/入社保/是否发放，必须由规则管理员或算薪负责人确认。

### 系统级薪资组件字典

每个标准薪资组件至少包含：

- 组件编码。
- 组件名称。
- 组件类型：收入、扣款、补贴、社保个人、社保公司、税、公司成本、对照值等。
- 是否发放给员工。
- 是否进入 PPh21 税基。
- 是否进入 BPJS 基数。
- 是否参与 Gross Up。
- 是否影响实发工资。
- 是否影响雇主成本。
- 默认正负方向。
- 适用规则版本。
- 生效月份。
- 停用状态。

### 客户级别名映射

- 客户原始 Excel 字段、客户习惯叫法、历史模板列名，可以映射到系统级标准薪资组件。
- 客户级别名映射允许预填，但不允许自动生效。
- 别名映射生效必须人工确认，并生成映射版本。
- 客户级别名不能改变标准组件的入税、入社保、是否发放等规则属性；如需改变，必须维护客户规则版本。

### V1 需求含义

- 字段映射时，Agent 需要区分“普通字段映射”和“薪资组件映射”。
- 未识别薪资组件不得静默并入“其他收入”。
- 未识别字段如果金额会影响应发、扣款、税、社保、实发或雇主成本，属于阻断项，必须完成人工确认、客户追问或规则配置后才能正式算薪。
- 未识别字段如果只是备注、部门、门店等非金额信息，进入普通字段待确认，不阻断算薪。
- V1 允许存在“其他收入/其他扣款”等兜底组件，但系统不得自动归入。
- 使用兜底组件必须由人工选择、绑定证据，并进入高风险清单。
- 薪资组件字典和客户别名映射都需要版本化，并绑定到 payroll run。
- 算薪确认包需要展示本期使用的薪资组件、客户别名、规则属性和映射来源。
- 如果客户 Excel 只给“应发工资合计”而没有组件明细，系统按已确认三福规则处理：作为未拆分税前应发输入，不由客服自行拆分组件。
- 薪资组件字典、客户别名或规则版本修改后，不得自动影响已存在的 payroll run。
- 相关未锁定 payroll run 需要标记为“需重新预检查/需重算”，由算薪人确认是否采用新版本。
- 已锁定 payroll run 永远保持原组件/规则快照，只能通过 correction run 处理后续更正。

## 24. 规则版本发布审批

### 已确认口径

- 规则管理员发布新规则版本时，V1 需要最小审批。
- 规则管理员负责起草规则版本。
- 算薪负责人/交付主管负责确认发布。
- 规则版本发布后不可编辑，只能停用或发布新版本。

### 适用范围

- 法规/公共规则：TER、PTKP、Pasal 17、BPJS、UMP/UMK、日历、THR、假期、加班等。
- 客户规则：计薪口径、假期影响、工资组件、BPJS 基数配置、JKK 比例、Gross Up 适用规则等。
- 薪资组件规则属性：是否发放、是否入税、是否入社保、是否参与 Gross Up、是否影响实发和雇主成本等。

### V1 需求含义

- 规则版本至少包含版本号、规则类型、适用客户/范围、生效月份、规则内容、起草人、审批人、发布时间、状态和变更说明。
- 草稿规则不得被 payroll run 正式引用。
- 已发布规则可以被 payroll run 引用，并在 payroll run 锁定时形成只读快照。
- 已发布规则不得原地编辑；发现错误时必须停用旧版本并发布新版本。
- 停用规则不得影响已锁定 payroll run，只影响后续新 run 或 correction run 的规则选择。
- Agent 可以基于资料库提示规则缺失、冲突或疑似过期，但不能自行起草生效版本、审批或发布规则。

## 25. 客户规则与公共法规规则冲突

### 已确认口径

- 公共法规底线永远优先。
- 客户规则只能在法规允许范围内覆盖。
- 系统发现客户规则疑似违反法规参数时，必须阻断规则发布。

### V1 需求含义

- 规则发布前必须执行冲突检查，至少检查客户规则与 TER、PTKP、Pasal 17、BPJS、UMP/UMK、THR、加班、假期等公共规则是否冲突。
- 客户规则冲突检查失败时，不得发布为生效版本。
- 冲突项需要展示冲突字段、客户规则值、公共法规规则值、适用月份、影响范围和处理建议。
- 如果属于法规允许的客户差异口径，必须记录依据、客户确认、审批人和生效月份后才能发布。
- Agent 可以解释冲突原因和建议追问客户，但不能绕过冲突阻断或自行发布规则。

## 26. 规则发布回归测试

### 已确认口径

- 规则发布前，V1 需要自动测试样例。
- 每个规则版本发布时，至少跑蓝色光标和三福的回归样例。
- 回归样例需要确认关键金额、人数和模板输出没有被意外改坏。

### V1 需求含义

- 规则版本从草稿进入发布审批前，系统必须执行回归测试。
- 回归测试至少覆盖蓝色光标和三福两条端到端样例。
- 回归测试输入应使用 docs 中的真实案例原始 Excel、已确认映射、规则版本和目标输出样本。
- 回归测试结果需要展示人数、应发、实发、PPh21、BPJS、雇主成本、导出模板结构等关键校验。
- 回归测试失败时，规则版本不得发布。
- 回归测试通过记录需要绑定到规则版本审批记录。
- 回归样例的人数、员工匹配和导出模板结构必须与预期结果完全一致。
- 回归样例金额差异绝对值超过 IDR 1,000 时提示，超过 IDR 10,000 时阻断规则发布。

## 27. 算薪结果计算解释与公式链

### 已确认口径

- 算薪引擎的计算结果，P0 必须保留每个字段的计算解释/公式链。
- 至少能解释每个员工的应发、税基、PPh21、BPJS、实发、雇主成本，是由哪些输入、规则版本和薪资组件组成的。
- 计算解释必须来自确定性的算薪引擎和规则快照；Agent 可以基于解释链生成自然语言说明，但不能编造计算依据。

### V1 需求含义

- 每个 payroll run 需要保存员工级计算 trace。
- 每个关键结果字段至少需要保存：输入字段、标准化数据版本、薪资组件、组件规则属性、中间计算值、规则版本、参数值、最终结果。
- 关键结果字段包括：应发工资、应税收入/税基、PPh21、BPJS KS、BPJS TK、员工个人承担、雇主承担、实发工资、雇主成本。
- 计算解释需要能反查到原始 Excel 来源、字段映射版本、员工主档版本、客户配置版本、汇率版本和规则参数版本。
- 算薪确认包、员工明细页、核查报告和归档视图必须能查看计算解释。
- 如果系统计算值与客户计算值或历史归档值存在差异，差异说明必须引用计算解释链，而不是只给一个差额数字。
- 已锁定 payroll run 的计算解释链必须随 run 一起归档，后续规则或主档变更不得影响历史解释。

## 28. 金额精度与取整规则

### 已确认口径

- V1 需要支持统一的金额精度与取整规则。
- 取整口径必须进入规则版本管理。
- 内部计算保留高精度，输出到 IDR 时按字段配置取整方式。
- 税、BPJS、实发工资、雇主成本等字段需要分别支持配置取整方式。
- V1 默认取整方式为四舍五入到 IDR 整数。
- 规则版本允许按字段覆盖取整方式为向上取整、向下取整或截断。
- 外币工资换算为 IDR 后不立即取整；保留高精度进入后续计算，最后按字段取整规则输出正式金额。

### V1 需求含义

- 规则版本需要包含金额精度、取整字段、取整时点、取整方式和适用范围。
- 取整字段至少覆盖：应发工资、应税收入/税基、PPh21、BPJS KS、BPJS TK、员工个人承担、雇主承担、实发工资、雇主成本。
- 系统计算 trace 必须保留取整前金额、取整方式、取整后金额和差额。
- 算薪确认包和核查报告需要能解释金额差异是否来自取整。
- 导出 Excel 使用取整后的正式金额；内部计算解释链保留取整前中间值。
- 取整规则变更不得自动影响已存在的 payroll run；未锁定 run 需要标记为“需重新预检查/需重算”，已锁定 run 只通过 correction run 更正。
- 如果客户计算值与系统计算值差异只来自已发布取整规则，系统应在差异核查中标记为“取整差异”，避免误报为算法差异。

## 29. THR 支持范围

### 已确认口径

- THR 进入 V1 P0，但范围先以蓝色光标真实案例端到端跑通为准。
- V1 需要支持蓝色光标案例里的 THR 原始输入导入、字段映射、标准化、计算、核查、确认、导出和归档。
- V1 需要建立通用 THR 规则数据结构。
- 复杂自动发放策略先列为 P1，不作为 V1 必须完整配置能力。

### V1 需求含义

- THR 作为薪资组件进入系统级薪资组件字典，并配置是否发放、是否入税、是否入 BPJS、是否影响实发和雇主成本。
- THR 规则版本至少需要支持宗教节日、员工信仰/适用节日、入职日期、在职状态、服务期间、计算基数、生效月份、发放月份和客户覆盖口径。
- 蓝色光标 payroll run 需要能识别 THR 输入文件/字段，并把 THR 纳入算薪结果和导出文件。
- THR 计算解释链需要展示输入来源、计算基数、服务期间、规则版本、取整方式和最终 THR 金额。
- 如果 THR 输入缺失、员工信仰/适用节日缺失、计算基数缺失或规则版本缺失，系统必须生成阻断项或追问项。
- 通用 THR 自动发放策略，例如按不同宗教节日自动生成批次、跨月发放、多规则组合，列为 P1。

## 30. 离职/年度清税与 BPA1

### 已确认口径

- 离职/年度清税进入 V1 P0。
- V1 必须支持蓝色光标 BPA1 离职个税报盘端到端。
- V1 不扩展成完整税务申报系统；申报流程自动化不在 V1 范围内。

### V1 需求含义

- 蓝色光标 payroll run 需要识别离职员工、离职日期、离职当月薪资、历史累计收入、历史已扣税额和清税所需字段。
- 算薪引擎需要支持离职月/年度清税计算，并生成员工级计算解释链。
- BPA1 导出必须与蓝色光标真实案例同结构。
- 离职员工必须进入高风险清单，并在算薪确认包中展示离职原因/日期、客户证据、清税结果、BPA1 输出状态。
- 离职/年度清税需要绑定规则版本、历史薪资归档、员工主档版本和客户确认记录。
- 缺少历史累计数据、离职日期、员工税务信息、规则版本或客户确认时，系统必须生成阻断项。
- 历史累计数据允许手工补录，但必须绑定有效证据，并进入高风险清单。
- 完全无证据的历史累计数据不得用于离职/年度清税计算。
- BPA1 文件作为交付输出和归档文件保存；政府平台申报、自动提交、申报状态回传不进入 V1。

## 31. 发薪记录与付款证据

### 已确认口径

- 发薪记录进入 V1 P0。
- V1 只记录已发/未发状态和付款证据归档。
- V1 不做银行付款流程、银行打款文件生成或支付执行。

### V1 需求含义

- 发薪记录需要关联 payroll run、客户、薪资月份、员工、实发金额、币种、发薪状态、发薪日期和付款证据。
- 发薪状态至少包括：未发、部分已发、已发、发薪失败、待更正。
- 付款证据可以是银行回单、付款截图、客户确认文件或其他有效付款凭证。
- 发薪记录需要支持员工级和批次级查看。
- 发薪记录与锁定 payroll run 绑定，不能反向修改已锁定算薪结果。
- 如果发薪后发现算薪错误，只能通过 correction run 处理，不得原地修改原 payroll run。
- 银行付款流程、付款审批、银行文件生成、支付接口、回单自动抓取列为 P1 或后续范围，不影响 V1 验收。

## 32. KS/TK 申报证据归档

### 已确认口径

- KS/TK 申报证据进入 V1 P0。
- V1 只做申报证据归档，不做政府平台申报流程。
- V1 不做政府平台提交、自动申报、申报状态回传或官方接口集成。

### V1 需求含义

- KS/TK 申报证据需要记录申报主体、客户、薪资月份、人数、缴费金额、官方凭证、关联 payroll run 和上传/确认人。
- 申报证据需要区分 BPJS KS 和 BPJS TK。
- 申报证据需要支持批次级和员工级关联；如果官方凭证只覆盖部分员工，系统必须记录覆盖范围。
- 社保账单或官方凭证不完整时，可以作为部分覆盖证据，但必须进入核查项或高风险清单。
- KS/TK 申报证据需要进入归档视图，并能从 payroll run、员工和社保计算结果反查。
- 政府平台申报操作、自动提交、状态同步、官方接口集成列为 P1 或后续范围，不影响 V1 验收。

## 33. PPh21 申报证据归档

### 已确认口径

- PPh21 个税申报证据进入 V1 P0。
- V1 至少归档 BPMP、BPA1 等导出文件，以及客户/内部确认记录。
- V1 不做税局平台提交、自动申报、申报状态回传或官方接口集成。

### V1 需求含义

- PPh21 申报证据需要关联 payroll run、客户、薪资月份、申报主体、员工范围、PPh21 金额、导出文件和确认记录。
- 蓝色光标 BPMP 在职个税报盘、BPA1 离职个税报盘需要作为 PPh21 申报证据归档。
- PPh21 申报证据需要支持批次级和员工级关联。
- 如果 PPh21 导出文件只覆盖部分员工，系统必须记录覆盖范围。
- PPh21 申报证据需要进入归档视图，并能从 payroll run、员工、个税计算结果和导出预览反查。
- 税局平台提交、自动申报、状态同步、官方接口集成列为 P1 或后续范围，不影响 V1 验收。
